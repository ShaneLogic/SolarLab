# R1 evidence revision five

Revision five is a development candidate. It does not imply independent
approval of a source commit, a trajectory, a parameter range or a new physical
criterion. The verifier is trusted code installed outside the supplied bundle.

## Checks

- All recorded statuses must match the caller-selected evidence revision.
  Failed runs receive the same source, committed-blob, frozen-input, contract
  and controlled-runtime checks as passed runs. A startup rejection lacking
  these records is still available to the byte-integrity checker; it is not
  accepted as a controlled research run.
- The operator-criterion disposition and supplemental four-case failure
  registry are frozen source roots with independent verifier constants.
  Neither a new outer manifest nor a candidate-side repin changes those roots.
- A consumed preparation must be a passed revision-five preparation with the
  same source, input, reference and policy artifacts. Its full parent package
  is archived and checked against a separately supplied manifest digest.
- The trusted verifier reevaluates saved preparation checks and the original
  QSS DC certificate at the recorded coordinates. It does not launch another
  DC optimization. The preparation policy is limited to the declared numerical
  refinements; it cannot introduce a relaxed physical gate.
- Result checking verifies internal canonical digests, declared identities,
  numerical sidecars and duplicated accepted-step records, together with
  relationships and summaries that can be reconstructed from saved records.
  The returned check scope distinguishes these from solver diagnostics that
  are only checked for range or consistency. Time integration is not replayed.

## Limits

A supplied external digest is an identity anchor, not an independent approval
or a signature proving that a historical execution happened. A consistently
fabricated whole history cannot be excluded by redundant JSON/NPZ copies.
Scientific interpretation still requires independent reproduction, convergence
and the stated trust in the launcher, interpreter, dependencies and Git store.
Historical environment, creation time and optimizer history are recorded
provenance, not independently recomputed facts.

Old preparation payloads lack the new policy and verification fields and must
be regenerated for new execution. Explicit legacy verification remains available
for historical evidence. In particular revision-three input from the reviewed
794dd7e/84f9131 lineage is recognized only in explicit revision-three mode.
Legacy results cannot acquire revision-five numerical or criterion checks.

## Development axes

The existing short functional run remains the default. The CLI additionally
supports declared temporal triples through (16,32,64), spatial intervals
128/256 and explicit logarithmic windows in development mode. Those records
use `R1-2-development` scope and are rejected by formal acceptance. Enumerating
or executing a 27-case matrix does not establish that it converged.

The four additional amplitude-ladder failures remain historical failed
observations. The original study-input bytes and its 21-case registry are
preserved; the runtime combines the separately pinned four-case supplement
without skipping calculations or changing acceptance thresholds.
